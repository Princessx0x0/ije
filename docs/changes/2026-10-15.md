# What changed on 15 October 2026, and why

One day's work took Ije from "signed in, placeholder page" to a working planner. A
traveller now signs in, tells Ije how they travel, plans a trip, and gets a day-by-day
itinerary of real places with real weather, built by an agent whose rules are
enforced in code and measured by evals.

This document is the record of what changed and the reasoning behind each change.
The decisions with lasting consequences are in ADRs 006 and 007
(`docs/decisions/`).

## 1. Routing after sign-in, and guests (PR #1)

**Problem.** `app/page.tsx` was a placeholder that showed "Signed in as" and offered
guests "Create an account" and "Sign out". There was no onboarding and no trips page.

**Change.**
- `/` reads `users/{uid}.persona` from Firestore. No persona sends you to `/onboarding`;
  otherwise you go to `/trips`. Guests and full accounts take the same path.
- The upgrade prompt for guests moved into a new account menu, as an optional "Save my
  account". Guest sign-out asks for confirmation inside the menu, not a browser dialog.
- `/sign-in` gives guests a "Not now, keep planning as a guest" link.

**Why.** CLAUDE.md asked for exactly this, and pushing guests to sign up before they
have seen any value loses them. Firebase lets a guest upgrade in place and keep their
uid, so nothing is lost by waiting.

## 2. Health data needs explicit consent (PR #1, extended in #2)

**Problem.** Onboarding collected diet, allergies and access needs with only an
information notice. These can be health data, and halal or kosher can reveal religious
belief: special category data under UK GDPR Article 9. A notice is not consent.

**Change.**
- Onboarding and Travel preferences show an unticked consent checkbox. The diet,
  allergy and access fields appear only once it is ticked. The wording covers the
  traveller and their travel group.
- Firestore records `consents.health = { granted, version, at }`. The version
  (`2026-10-15`) lets us re-ask whenever the wording changes.
- Unticking and saving deletes the fields from the profile and clears `party_needs`
  on every trip, in one atomic batch.
- Group needs on the trip form only appear when consent is on record.

**Why.** Explicit consent is the most likely lawful condition for this data. It is
assumed until the governance phase confirms it (`docs/privacy-governance.md`). Without
it, the app would be collecting special category data with no lawful basis.

## 3. Firestore rules, deployed and tested (PR #1, #2, #3)

**Change.**
- `firestore.rules`: each user can reach only `users/{their uid}`. Health fields and
  trip `party_needs` are refused unless consent to the current wording is on record.
- `firebase.json` and `.firebaserc` let the rules be deployed from the repo. They were
  deployed to `ije-travel-511008`.
- `npm run test:rules` runs 29 tests on the Firestore emulator. The suite was
  mutation-checked: deliberately weakened rules made the right tests fail.

**Why.** Firebase web config is public by design, so the rules are the only thing
protecting the data. Rules that are not tested are a guess.

## 4. The privacy policy waits for governance (PR #1)

**Change.** Instead of a privacy page, `docs/privacy-governance.md` records what Ije
collects, where each piece goes, and the decisions a policy depends on: the
controller, the lawful basis, the UK to US transfer mechanism, retention, a DPIA, and
others.

**Why.** A policy that describes undecided things is worse than none. The worksheet
is kept current as features change the data, and the policy is written from it.

## 5. Light only (PR #2)

**Problem.** On a dark-mode machine Ije switched to its near-black palette, and you
did not want it.

**Change.** `tokens.json` sets `color.followSystem: false`, so the generated CSS no
longer follows the OS. The viewport declares `color-scheme: light`, and an Ije-styled
404 page replaces Next's default (which had its own dark mode). The dark palette is
kept as a design record behind an explicit opt-in.

## 6. Planning a trip (PR #2)

**Problem.** After onboarding the traveller landed on "No trips yet", with no way
forward.

**Change.**
- **First run goes straight to planning.** A new user's first onboarding save opens
  `/trips/new`, and an empty trips list redirects there too.
- **The trip form asks who is going first.** Budget follows, labelled for one person or
  for the group, and group needs appear only for group trips. This was your feedback:
  "group budget" made no sense before anyone had said it was a group.
- **Vibe sliders:** pace, local or well known, and style.
- **The itinerary canvas** (`/trips/{id}`) plans automatically on the first visit. It
  saves the result to Firestore, so reloads do not re-plan, and has a hideable side
  chat for changes.
- **Failures are visible.** A failed agent run shows Ije's own message with Try again,
  instead of only CopilotKit's developer banner.

**Why.** No dead ends: every screen has a next step.

## 7. A great agent (PR #3)

### 7.1 The agents-cli project layout

**Change.**
- `agent/` is now a Python package: `agent/agent.py` defines `root_agent`, and
  `agent/main.py` keeps AG-UI serving and Firebase identity unchanged.
- One Python project lives at the repo root (ADK 2.5 to 2.11). After the move, AG-UI
  was checked live and still refuses runs without a token.
- Removed from what `agents-cli scaffold enhance` generated:
  - `fast_api_app.py`, which exposed ADK's web UI and A2A routes with no Firebase
    identity, a way round ADR 005
  - the unused Terraform
  - an `.env.example` that suggested API keys, against ADR 002

**Why.** The eval tooling you chose needs this layout. Ije's own serving and identity
must remain the only way into the agent.

### 7.2 Real data from Google Maps Platform (ADR 006)

**Change.** The agent uses Places API (New) and the Weather API. Both were verified to
accept OAuth, so the agent uses its own identity and **there is no API key anywhere**.
Google Cloud changes made:
- the two APIs were enabled
- the frontend service account was granted `serviceUsageConsumer`, so it can look up
  place names for display

**Maps terms, and how Ije keeps them:**
- **Only place IDs, our own text and links are stored.** Names and addresses are
  fetched live through `/api/places`, which only signed-in users can call because each
  lookup is billed.
- **Weather and coordinates are never stored.**
- **Attribution:** the canvas shows "Places and weather from Google Maps".

**Why Google.** It is the same vendor and billing as the rest of Ije, so no new party
receives data, and the data has stable IDs and good accessibility fields.

### 7.3 The tools and their guardrails

| Tool | What it does |
| --- | --- |
| `get_forecast` | Real forecast for trip days within 10 days. Further out, gives the date it becomes available and no invented weather. |
| `search_places` | Places near the destination, with opening hours, wheelchair access and vegetarian flags. |
| `update_itinerary` | Saves the plan, only if it passes the rules below. |
| `update_stays` | Real hotels, plus an Airbnb search link built by our code. |

These rules are **enforced in code** (`agent/tools/rules.py`, 13 unit tests), not only
asked for in the prompt:
- Every day has a morning, afternoon and evening item, plus at least one place to eat.
- Every place came from a search. Invented IDs are rejected.
- A reason never repeats the place's name, so names never reach Firestore.
- Diet and allergies are added to every food search, and wheelchair access to every
  search, for travellers who need it.
- A fish or shellfish allergy rejects seafood-type restaurants.
- After saving, the agent is told to remind the traveller to confirm allergens, and to
  name places whose step-free access is unconfirmed.
- When Gemini writes a tool call as Python inside a made-up `google:python_interpreter`
  tool, the call is parsed with `ast` (never executed, literals only) into the real
  call.

**Why in code.** The evals showed that instructions alone fail some of the time. A rule
in code fails never.

### 7.4 Gemini through the global endpoint (ADR 007)

**Change.** The deploy now sets `GOOGLE_CLOUD_LOCATION=global`, matching local
development. The model retries `429` errors with backoff.

**Why.** It is Google's recommended default for Gemini, and it routes around the
capacity errors seen during evals. Stored data stays in `us-central1`. Prompts may be
processed in any region, which the governance worksheet now records.

### 7.5 Evals: how we know it is good

`tests/eval/README.md` explains how to run them. There are two metrics:
- `plan_rules` (code): what the agent actually did. It must check the forecast first,
  have an itinerary or stays accepted, call no unknown tools and make no unrequested
  changes.
- `ije_judge` (Gemini 2.5 Pro): each case's expected behaviour, with hard caps for
  false claims, invented data and ignored needs.

**The bar:** `plan_rules` 1 and `ije_judge` at least 4 on every case.

| | plan_rules | ije_judge |
| --- | --- | --- |
| Baseline | 0.8 mean | 3.4 mean |
| Final, 5 core cases | 1 on every case | 4, 4, 5, 5, 5 |
| Final, 3 held-out cases | 1 on every case | 5, 5, 5 |

The evals found three real failures, and all three are fixed:
1. **An unsaved plan the agent claimed was done.** It called a non-existent Python tool
   ten times, saved nothing, then said "Expect cloudy weather…".
2. **A peanut allergy left out of the restaurant searches.** This was found by a
   held-out case, which is why held-out cases exist.
3. **A seafood restaurant picked for a shellfish allergy.**

**On honesty.** One judge rule was refined. An invented place that the tool *rejected*
and the agent corrected now costs one point instead of capping the score at 2, because
the guardrail is what stopped it reaching the traveller. Anything invented that reaches
the traveller still caps at 2.

**Tooling.** agents-cli 1.10 cannot seed trip state on ADK 2.11 (ADK now refuses
client-supplied state events), so `tests/eval/agents_cli_eval.py` seeds it the way ADK
accepts. Remove it once agents-cli is fixed.

### 7.6 What the traveller sees

- Place names on cards, with "Open in Google Maps".
- A forecast badge on each day, or "Forecast available from …" for trips further out.
- A "Where to stay" section with real hotels and an Airbnb search.
- The Google Maps attribution line.

**Frontend (Cloud Run): first deployment.**
- **Live at https://ije-frontend-788712976210.us-central1.run.app**
- Built by Cloud Build from `frontend/Dockerfile` with `scripts/deploy-frontend.sh`,

  blocks `allUsers`. Rather than weakening that policy, the service runs with Cloud

  approach for public services under that policy (ADR 005 addendum). The agent behind
  it stays IAM-only.
- Its address was added to Firebase Auth's authorised domains, so Google sign-in
  works there.
- Checked live:
  - pages serve, in the light theme
  - the CopilotKit runtime answers
  - `/api/places` refuses callers without a Firebase token

**Firestore rules** were deployed earlier in the day and are covered by the tests.

**Not yet done:** a signed-in walkthrough on the live site (planning a trip end to
end). It was left for a person, to avoid creating test accounts in production.

### Two fixes after going live

- **Every sign-in was refused** ("incorrect aud claim"). On Agent Runtime,
  `GOOGLE_CLOUD_PROJECT` holds the project number, and the agent used it as the
  Firebase project ID. It now reads `FIREBASE_PROJECT_ID`, and token errors name
  the real cause (expired, revoked, wrong project or server error) instead of
  always saying "invalid". This bug predates today and was hidden until the
  first live sign-in.
- **The sign-in check and the Maps calls were rejected** as unauthenticated.
  Agent Identity tokens are certificate-bound, and these calls send plain
  tokens. You chose "working now, secure later": the binding is switched off
  for now (ADR 008), with a tracked follow-up to move these calls to mTLS and
  switch it back on.
